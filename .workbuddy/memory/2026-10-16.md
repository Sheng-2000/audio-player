## ✅ git push 被拦截时的 API 绕过方案（已验证可用）
当 `git push` 卡在 `Total N (delta M)` 后丢弃 ACK 时，改用 GitHub REST API 直接重建并推送提交，绕过 git 协议：
1. 用 `python3` + `urllib`（**不要**用有依赖的 requests）调 `api.github.com`。
2. token 从 `git config --get remote.origin.url` 解析（`https://<tok>@github.com/...`），请求头 `Authorization: Bearer <tok>`，**绝不打印 token**。
3. 流程：`POST /git/blobs`（新文件内容，音频用 base64/文本用 utf-8）→ `GET /git/trees/<base>?recursive=1` → 剔除旧路径、加入 rename/新条目 `POST /git/trees` → `POST /git/commits` → `PATCH /git/refs/heads/main`。
4. **两个 SHA 坑（导致本地提交 SHA ≠ 远程，产生分叉）**：
   - GitHub 提交 API 创建的提交，消息**不带尾换行**（不像 `git commit -m` 会自动加 `\n`）。
   - 时区保留原始 `+0800`（API 返回 UTC `Z` 是展示值，原始对象仍是 `+0800`）。
   - 因此用 `git commit-tree` 在本地重建同一对象时，必须：`GIT_AUTHOR_DATE/COMMITTER_DATE="<ts> +0800"` 且消息**用 `printf` 不带 `\n`** 经 stdin 传入，才能复现远程 SHA。
5. 复现出远程 SHA 后，`git reset --hard <同一SHA>` 即可让本地与远程**零分叉对齐**（树与 blob 本地已存在，无需重新下载）。
6. 实测：API 上传速率约 0.38 MB/s（13.4MB 音频 ≈ 35s），远快于 git ACK 丢弃的卡死；`api.github.com` 请求/响应正常。
